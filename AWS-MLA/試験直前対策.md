> 誤り数2以上の問題を分析し、繰り返しミスしているポイントだけを抽出しています。

| # | 問題のシナリオ | 正解 | 罠・理由 |

## 1. 推論エンドポイントの使い分け

シナリオのキーワードで即判断できるようにする。

| キーワード | 正解 |
|---|---|
| 大容量（5GB以上）・処理時間が長い・コスト削減 | **非同期推論** |
| 深夜はゼロ・トラフィック変動大・コールドスタートOK | **サーバーレス推論** |
| ミリ秒応答・低レイテンシ必須 | **リアルタイム推論** |
| 大量データを一括処理・リアルタイム不要 | **バッチ変換** |
| 1日1時間だけピーク・インフラ管理したくない | **サーバーレス推論**（プロビジョニング同時実行数設定） |

### よく混ざるパターン

- 「大量の画像データ・一度に多くのリクエスト・夜間はコスト削減」→ **非同期推論**（バッチ変換ではない）
- 「数秒以内のレスポンス必要・秒間数百リクエスト」→ **リアルタイム推論**（非同期ではない）
- 「30分かかる処理・翌朝までに完了でOK」→ **非同期推論**（Lambda最大15分なのでLambdaはアウト）

## 2. SageMaker ツールの混同

### 2-1. ML Lineage Tracking（第2回Q17）

「データ → トレーニング → モデルの経路を追跡・監査・再現性確保」  
→ **SageMaker ML Lineage Tracking**

- Pipelines：ワークフローの自動化
- Model Registry：モデルのバージョン管理
- **Lineage Tracking：データとアルゴリズムの使用履歴を記録**

### 2-2. Inference Recommender（第2回Q47 / 第3回Q39）

「最適なインスタンスタイプを選びたい・カスタムトラフィックでロードテストしたい」  
→ **SageMaker Inference Recommender**

| ジョブタイプ | 内容 |
|---|---|
| デフォルト（推論レコメンデーション） | 標準ロードテストで素早く推奨 |
| アドバンスト（エンドポイントレコメンデーション） | **カスタムトラフィックパターンで詳細評価** ← ここが出る |

- Compute Optimizer：EC2/EBS/Lambda向け、SageMaker推論インスタンスは対象外
- Trusted Advisor：SageMakerインスタンスタイプに非対応

### 2-3. Role Manager（第2回Q48）

「ML Engineer / Studio User / Ops など役割ごとのアクセス権管理・最小オーバーヘッド」  
→ **SageMaker Role Manager**（ペルソナを設定して関連付け）

- IAMロールを手動で作るより低オーバーヘッド

### 2-4. 高速ファイルモード（第3回Q40 / 第4回Q20）

「大規模データ・既存のファイルモードコードを変更せずに高速化したい」  
→ **高速ファイルモード（Fast File Mode）**

- パイプモード：ファイル形式やコードの変更が必要 → **要件「コード変更なし」があればパイプモードはアウト**
- 分散トレーニング：データ読み込み速度ではなく計算を並列化するもの

### 2-5. SageMaker Neo（第2回Q38）

「エッジデバイスへのデプロイ・リソース制限あり・推論最適化」  
→ **SageMaker Neo**（モデルをコンパイルしてハードウェア最適化）

- Elastic Inference：EC2/SageMakerエンドポイント向け、エッジ不可
- IoT Core：デバイス接続・管理サービス、ML最適化機能なし

## 3. Bedrock のハイパーパラメータ

### 多様な応答・クリエイティブな文章を作りたい

| パラメータ | 多様性UP | 多様性DOWN |
|---|---|---|
| Temperature | **大きくする** | 小さくする（0に近い→決定論的） |
| Top_k | **大きくする** | 1にする（常に最高確率のトークンを選択） |
| Top_p（Nucleus Sampling） | **0.8程度が適切** | 低すぎると候補が絞られる、1.0はノイズ混入 |

### 罠問題（第3回Q24）

「多様でクリエイティブなキャッチコピーを生成したい」  
→ **Top P = 0.8**（0.8が「適切なバランス」の正解）  
- Top P = 1.0 は候補が多すぎてノイズが混入するため不正解
- Top K = 1 は常に同じ単語→多様性ゼロ
- Temperature = 0.1 は決定論的→多様性ゼロ

## 4. バイアスの種類

| バイアス名 | 説明 | 例 |
|---|---|---|
| **DPL**（Difference in Positive Proportions in Labels） | グループ間の陽性ラベル率の差 | 中高年80%承認 vs 若年層50%承認 → DPL = -30% |
| **CI**（Class Imbalance） | 特定グループのサンプルが少ない | 少数民族のデータが全体の2%しかない |
| **選択バイアス** | データ収集時にサンプルに偏り | 過去のキャンペーン参加者のデータのみ使用 |
| **ラベルバイアス** | ラベル付けが不整合 | アノテーターによって基準が異なる |
| **表現バイアス** | 現実を正確に反映していない | 現実の分布と異なる比率でデータが収集されている |

## 5. Lookout サービスの区別

| サービス | 何を対象にするか |
|---|---|
| **Lookout for Equipment** | IoTセンサーデータ・工場設備の予兆保全・機械学習不要 |
| **Lookout for Metrics** | ビジネスメトリクス（売上・クリック数・CTRなど）の異常 |
| **Lookout for Vision** | 画像ベースの外観検査・製品の欠陥検出 |

「IoTセンサー・機器の異常・ベースラインと比較・ML専門家不要」→ **Lookout for Equipment**

## 6. Feature Store のモード（第3回Q25）

「S3+Athena（バッチ）と Firehose（ストリーミング）の両方から特徴量を取り込みたい」  
→ **オフラインストアとオンラインストアの両方を使用**

| モード | 用途 |
|---|---|
| **オフラインストア**（S3） | バッチ処理・履歴データ・Athenaクエリ |
| **オンラインストア** | リアルタイム・低レイテンシ・Firehoseなどストリーミング |

## 7. VPC ネットワーク

### VPC エンドポイントの種類（第1回Q64）

| 種類 | 対象サービス | 料金 |
|---|---|---|
| **ゲートウェイ型** | S3、DynamoDB のみ | 無料 |
| **インターフェイス型** | SageMaker など多数 | 有料 |

**→ S3 = ゲートウェイ、SageMaker = インターフェイス（逆は不正解）**

### NAT Gateway（第3回Q4）

「SageMaker（プライベートサブネット）から外部への通信を許可、インバウンドは拒否」  
→ **パブリックサブネットに NAT Gateway を設置してルーティング**

- NAT Gateway はアウトバウンドのみ許可、インバウンドは拒否する特性がある
- インターフェイス VPC エンドポイントは AWS サービスへのプライベート接続用（外部企業へは不可）

## 8. Bedrock クロスリージョン推論（第3回Q28 / 第4回Q28）

「複数リージョンへリクエスト分散・1リージョンのリクエスト上限回避・可用性向上」  
→ **Amazon Bedrock クロスリージョン推論**

- Bedrock単体で完結、CloudFront や Global Accelerator など他サービスは不要
- 各リージョンに個別モデルをデプロイする必要もなし

## 9. その他の頻出ミス

### 9-1. データラベリング（第3回Q8）

「大量テキストへのラベリング・最小オーバーヘッド・人間によるチェック」  
→ **Amazon Mechanical Turk**（クラウドソーシング・HIT）

- Rekognition：画像認識、ラベリングサービスではない
- Textract：OCR
- Lookout for Vision：画像検査

### 9-2. KMS キーの管理（第3回Q11）

「暗号化キーを**自社で作成・定期的にローテーション**したい」  
→ **KMS カスタマー管理キー（CMK）を手動ローテーション**

- AWS管理キー → 自動ローテーションあり、ただし「自社で管理」の要件を満たさない
- CloudHSM → 専用ハードウェアで厳格管理、CMKより過剰

### 9-3. CloudFormation Parameter（第3回Q12）

「デプロイ時にユーザーがインスタンスタイプを選択できるようにしたい」  
→ **Parameter セクション**を使用

| セクション | 用途 |
|---|---|
| **Parameter** | デプロイ時にユーザーが動的に値を指定 |
| Mappings | リージョンごとの固定値を定義 |
| Conditions | 条件に基づいてリソース作成を制御 |
| Resource | AWSリソースの定義 |

### 9-4. Hyperband（第3回Q18 / 第1回Q63）

「ハイパーパラメータチューニングの時間を短縮・低パフォーマンスのトライアルを早期停止」  
→ **Hyperband**

- **Hyperband**：低パフォーマンスのジョブを早期停止 → 良い構成にエポックを再割り当て
- グリッドサーチ：全組み合わせを試す（計算コスト最大）
- ランダムサーチ：ランダムな組み合わせを試す（早期停止なし）
- ベイジアン最適化：過去の結果を基に次の探索を決定（反復改善向け）

### 9-5. keep_alive_period_in_seconds（第2回Q54）

「30分ごとに連続してトレーニングジョブを実行・インスタンス起動時間を短縮」  
→ **keep_alive_period_in_seconds = 1800**（30分 = 1800秒）

- 0秒に設定するとジョブ終了後すぐにインスタンスが終了 → 毎回起動時間がかかる

### 9-6. Kinesis ホットシャード（第3回Q17）

「特定のシャードにデータが集中（ホットシャード）・処理パフォーマンスが低下」  
→ **パーティションキーにランダムなプレフィックスを追加**してデータを分散

### 9-7. AWS Compute Optimizer（第2回Q18）

「EC2インスタンスの負荷が不均一・コスト最適化・適切なサイズに移行」  
→ **AWS Compute Optimizer**（EC2/EBS/Lambdaのリソース最適化を推奨）

- Cost Explorer：コスト可視化のみ、推奨機能なし
- Budgets：予算設定・通知のみ

### 9-8. SageMaker Model Monitor の設定手順（第2回Q57）

正しい手順：
1. SageMaker Endpoint を作成し **data_capture_config** を設定して推論データをS3に保存
2. Model Monitor でベースラインを作成し **baseline_dataset にトレーニングデータのS3パス**を指定
3. 監視スケジュールを作成

→ ベースラインを設定しないと比較対象がないため検出不可

## 10. SageMaker Script Mode（第2回Q8 / Q35）

「既存のTensorFlowスクリプトを最小限の変更でSageMakerに移行したい」  
→ **SageMaker スクリプトモード**

- 既存スクリプトをそのまま利用、環境変数でS3パスを指定
- SageMaker固有のAPIに依存しない柔軟性
- モデルアーティファクトをS3に保存した上でスクリプトモードを使用
